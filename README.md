# 社区垃圾分类督导与误投整改平台

> React 18 + TypeScript + Vite + Zustand 单页应用；Nginx 容器化部署，开箱即用的演示数据与四类角色账号。

## 原始需求

> 设计社区垃圾分类督导与误投整改页面，可使用 React、TypeScript 和 Zustand。督导员在投放点记录桶位、时段、居民楼栋、垃圾类型、误投照片、是否当场劝导和居民是否配合。页面根据湿垃圾、可回收物、有害垃圾和大件垃圾的不同规则，展示对应的处置要求和后续流向。居民扫码投放时，页面显示个人积分、近期误投提醒和本楼栋分类表现；督导员发现误投后，可以把证据绑定到楼栋、住户或匿名事件。清运人员到场时，若桶内污染严重、湿垃圾破袋、可回收物混入厨余或有害垃圾未单独封存，清运反馈会影响该投放点的整改任务。社区工作人员需要根据误投高发时段、楼栋、垃圾类型和居民反馈安排宣传、桶位调整或上门指导。整改完成后，督导复查、居民积分恢复、清运质量和物业保洁成本都要回到同一投放点档案。居民教育完成后，页面还会保留楼栋宣导、桶边值守和清运反馈之间的关系，社区可以判断下一步该做上门沟通还是调整投放设施。页面还要展示每个投放点的整改进度和清运反馈，社区工作人员可以判断问题来自居民习惯、桶位设计、督导缺位还是物业清洁不足。长期高发点位会进入专项治理清单。

## 一键启动（宿主 Docker Compose）

前置条件：宿主已安装 Docker 与 Docker Compose 插件。

```bash
# 1. 准备环境变量（可按需改端口）
cp .env.example .env

# 2. 构建并后台启动（多阶段构建，容器内以非 root 用户运行，内置 HEALTHCHECK）
docker compose up -d --build

# 3. 查看实际映射端口（避免硬编码端口冲突）
docker compose port app 8080

# 4. 浏览器访问（以下以默认 3023 为例）
#    http://<宿主IP>:3023
#    健康检查： http://<宿主IP>:3023/healthz

# 5. 验证结束释放资源
docker compose down
```

`.env` 说明：

| 变量 | 说明 |
| --- | --- |
| `CC_PUBLISH_PORT` | 发布到宿主的端口，容器内部固定监听 8080 |
| `COMPOSE_PROJECT_NAME` | Compose 项目名（验证环境固定，勿改） |

本工程只发布应用 Web 端口，无数据库/缓存依赖服务：演示数据内置在前端，运行期数据通过浏览器 `localStorage` 持久化（Zustand `persist`），顶栏「重置演示」可一键恢复种子数据。

## 建议的业务流验证路径

1. 用 `supervisor` 登录 → 督导记录页新登记一起误投，切换垃圾类型可看到**湿/可回收/有害/大件各自的处置要求与后续流向**；证据可选绑定住户 / 楼栋 / 匿名。
2. 用 `hauler` 登录 → 在清运反馈页勾选「桶内污染严重」等情形并关联事件 → 提交后事件自动升级为整改中、生成整改任务。
3. 用 `supervisor` 打开事件详情 → 下发/完成整改 → 复查（可演示不通过退回）→ 登记教育（楼栋宣导/上门/桶边值守）→ 复查通过后给居民恢复积分 → 三条件齐备自动闭环。
4. 用 `community` 登录 → 社区研判页查看高发时段/楼栋/类型与居民反馈聚类，逐点位查看四类根因得分（居民习惯/桶位设计/督导缺位/物业清洁不足）并安排宣导、值守、桶位调整或上门指导。
5. 点位档案页查看同一点位的整改进度、清运质量、保洁成本、宣导与值守关系链；专项治理页查看自动识别与人工挂牌的长期高发点。
6. 用 `resident` 登录 → 查看王阿姨积分冻结、误投提醒与 3 号楼分类表现。

## 技术结构

```
src/
├── types.ts                 # 领域模型（事件、清运、档案、专项清单……）
├── data/
│   ├── rules.ts             # 四类垃圾处置规则与流向
│   ├── seed.ts              # 演示种子数据
│   └── accounts.ts          # 四个演示角色账号
├── lib/analytics.ts         # 整改进度/根因诊断/高发规则/楼栋表现
├── store/useStore.ts        # Zustand store（全部业务动作 + localStorage 持久化）
├── components/
│   ├── ui.tsx               # 徽章/弹窗/图表/进度条/Toast
│   └── EventDetailModal.tsx # 事件整改-复查-教育-积分闭环操作
└── pages/                   # 工作台/督导/居民/清运/社区研判/点位档案/专项治理
```

- **状态管理**：Zustand + `persist` 中间件；清运反馈、整改、复查、教育、积分恢复等均为显式 action。
- **闭环规则**：事件需同时满足「督导复查通过 + 居民教育完成（+ 绑定住户的积分恢复）」才自动闭环。
- **根因诊断**：由劝导/配合、反复误投住户、清运四类问题、设施类居民反馈、值守排班、保洁成本等信号加权归一化到四类根因，并给出下一步动作建议。
- **无外部依赖**：纯前端 + Nginx 静态托管，适合隔离环境一键部署。
